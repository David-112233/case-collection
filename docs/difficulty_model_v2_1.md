> **本版相对旧版的根本变化：**
> 1. **废弃原 (A, B, C) 三维打分模型。** 旧模型依赖人类先验估计输入/推理/输出复杂度，在前 20 个静态案例的小规模评测中未能拉开难度档差距（即测量学意义上的"区分度不足"），故整体弃用。
> 2. **改为两层结构：** 第一层是**动态类型档（T1–T6）**，按"驱动方式"对案例做先验分类；第二层是**经验难度档（简单/中等/困难）**，由被测模型的**实测得分分布**跨类型统一标定，反向确定。
> 3. **难度不再由人拍板，而由数据反推。** 这一转向的依据见附录 A 的文献综述。

> **v2.1 修订（仅涉及第一层 T2/T3 的边界，第二层不动）：**
> 原 T2/T3 边界用**触发方式**（自动 vs 用户操作）划线，把"按钮 hover 换色"与"checkbox-hack 手风琴"划进同一档，从而给前者分配了同样的 D4 权重（50%）。试点案例 case-04（仿 Facebook 登录/注册页，动态部分仅"提交按钮 hover 换色 + transition"，静态部分含 21 个业务元素、16 条尺寸色值约束）暴露了这一代理关系不成立：该案例的区分度绝大部分来自静态部分，却只能拿到 30% 权重（D1 20% + D2 10%）——这与 `scoring_rubric_v2` 附录 C 改动 1 批评 v1"统一 70%"时的论证是同一个，只是换到了另一个档位重演。
> **v2.1 改为按"动态部分承载多少难度与区分度"划线**（即 §1.2 的权重设计原则）：**瞬时、自动还原、无状态载体的悬停/聚焦反馈下沉至 T2**；T3 收窄为**真正的状态机**（状态可保持）与**跨元素结构性显隐**。详见 §3.3。

## 一、为什么要弃用旧的先验难度模型

### 1.1 旧模型的问题

旧模型用三元组 (A, B, C) 三个维度各 1–3 分、相加得 3–9 分来先验地估计难度。在前 20 个（全部为静态）案例的小规模评测中，这套划分**未能在不同"难度分"的案例之间拉开实测得分差距**——高难度分的案例和低难度分的案例，模型得分都挤在 8.5 分附近。

用测量学的语言说，这是**区分度（discrimination）不足**：一个难度指标如果不能把强弱不同的题目/模型分开，它就没有测量价值。经典测验理论明确指出，几乎所有对象都得高分（或都得低分）的题目携带的信息量极低。旧模型正是如此。

### 1.2 更深层的原因：人类先验与模型实感错位

前端代码生成任务有一个反直觉的事实：**人类出题者并不知道大模型觉得哪种案例难。** 我们凭直觉认为"元素多、布局复杂 = 难"，但模型的难点可能完全在别处（例如某个反直觉的纯 CSS 机制模型压根没学会，而元素再多它也能堆出来）。

测量学研究印证了这一点：在对大模型拟合难度模型时，会发现大量题目的"难度随能力单调递增"这一基本前提被违背——**难度对不同模型未必一致、未必单调**。这意味着任何"人类先验拍难度"的方案都有系统性错位风险。因此，正确的方向是：**让模型的实测表现来定义难度，而非让人类的直觉来定义。**

## 二、两层结构总览

本模型将"案例是什么类型"与"案例有多难"彻底解耦为两个独立的层。

| 层 | 名称 | 性质 | 如何确定 | 举例 |
| :---: | :--- | :--- | :--- | :--- |
| **第一层** | 动态类型档 T1–T6 | **先验、确定的分类** | 由出题者按"驱动方式"直接判定，**不需要实测** | 一道滚动进度条题 → T5 |
| **第二层** | 经验难度档（简单/中等/困难） | **后验、由数据反推** | 由被测模型群的**实测平均得分**跨类型统一标定 | 该 T5 题实测均分 5.2 → 落入"困难"档 |

**两层的关系（关键，务必理解）：**

- 类型档 **不等于** 难度档。T 档序号大 **不保证** 更难。实测中完全可能出现"T4 比 T3 简单"——例如 `scroll-snap`（T4）是声明式、模型常见，反而比反直觉的 `:has()`（T3）容易。
- 难度档是**横切**六个类型档的：一道 T3 题和一道 T5 题，只要实测均分落在同一区间，就属于**同一难度档**。
- 因此**绝不是**"在每个类型档内部各自再分三档"（那会切出 18 个格子，样本无法支撑，且失去跨类型可比性）。而是**把所有案例的实测得分汇到一起，统一切三档**。

## 三、第一层 · 动态类型档（T1–T6）

**定位：** 按"页面的动态行为由什么驱动"对案例做先验分类。这是一个**技术分类维度**（类似图书馆分类号），出题时即可确定，不依赖任何实测。它决定了案例考察哪种能力、是否启用 D4 动效评分、评分是否需要渲染态断言。

### 3.1 六档定义

|   档    | 名称           | 驱动方式（判定关键）                                                                              | 典型纯 CSS 机制                                                                                      | 典型样本                                                                           |
| :----: | :----------- | :-------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------- |
| **T1** | 纯静态          | 无动态                                                                                     | flex / grid 布局、文档流                                                                              | 登录卡片、404 页、静态落地页                                                               |
| **T2** | 微动效（时间或悬停驱动） | 二者之一：①页面加载后**按时间自动**发生；②**悬停/聚焦触发、指针或焦点一离开即自动还原**，且变化只作用于被指向元素自身。**均不产生需要保持的状态**        | `transition`、`@keyframes` + `animation`；`:hover` / `:focus` / `:active` **自反馈**                 | 装饰元素持续旋转、加载动画、自动渐入；按钮 hover 换色、卡片 hover 抬升、输入框聚焦变色、链接下划线滑出                     |
| **T3** | 交互状态驱动（状态机）  | 二者之一：①用户显式操作（点击/勾选/跳锚）使页面进入一个**会保持的新状态**，操作结束后不自动回退；②悬停/聚焦**跨元素**驱动**其它元素**的显隐、展开等结构性变化 | `:checked` / `:target` / `:has()`、`<details>`、Popover；`:hover` / `:focus-within` **+ 后代/兄弟选择器** | 开关、手风琴、标签页、纯 CSS 模态/灯箱、下拉菜单、汉堡菜单、CSS 轮播、表单实时校验；hover 展开的二级菜单、hover 唤出的 tooltip |
| **T4** | 滚动驱动（基础）     | **滚动位置**驱动的吸附/对齐（离散停靠点）                                                                 | `scroll-snap-type` / `scroll-snap-align`                                                        | 整屏纵向 snap、横向图片画廊、snap 轮播                                                       |
| **T5** | 滚动驱动（进阶）     | **滚动位置连续驱动**动画进度                                                                        | `animation-timeline: scroll()` / `view()`、`animation-range`                                     | 滚动进度条、进入视口淡入/缩放、视差、滚动联动                                                        |
| **T6** | 高级组合         | **混合驱动**，或依赖需注册/命名才能生效的高级特性                                                             | `@property` 可动画自定义属性、View Transitions、scroll + VT 组合、`counter()` / 纯 CSS 图表                     | 渐变流动、conic 光效、数字滚动计数、纯 CSS 柱状图、滚动触发整屏视图切换                                      |

### 3.2 判定流程

读 `motion_constraints` 与 `functional_requirements` 中的动态描述 → 问一个问题：**"这个视觉变化是谁在驱动的？"**

```
没有任何变化                                   → T1
页面自己按时间在变（不用户操作、不滚动）             → T2
悬停/聚焦才变，但只改被指向元素自身、移开即自动还原    → T2
点/选/勾/跳锚使页面进入一个会保持的新状态           → T3
悬停/聚焦驱动了【其它】元素的显隐或展开              → T3
滚动时页面吸附到停靠点                            → T4
滚动时某动画进度跟着滚动条连续推进                   → T5
需要注册属性/命名视图/组合多种机制才成立              → T6
```

> 类型档是"名义分类"，不带难度含义，因此**不设简单/中等/困难**。难度完全交由第二层。

### 3.3 T2 / T3 边界（v2.1 新增）

**为什么单独立一节：** T2 与 T3 是六档中唯一因 v2.1 重划而边界改变的一对，且现实案例最容易踩在两者之间（"hover 到底算哪档"）。其余各档边界（T3/T4、T4/T5、T5/T6）沿用 v2 不变。

**判定用两问，顺序固定：**

```
问 1：这个变化在触发条件撤销后（松开鼠标 / 移走焦点 / 不再操作），会自动回到原状吗？
      会自动还原  → 继续问 2
      不会，状态被保持住 → T3（有状态载体：checkbox / radio / :target / details / :has() 条件源）

问 2：变化作用在谁身上？
      只作用于被悬停/聚焦的那个元素自身 → T2
      作用于其它元素（子菜单展开、tooltip 显现、面板滑出）→ T3
```

**两问背后的判据，写明以便复用：**

| 判据 | 含义 | 为什么它代理"考察强度" |
| :--- | :--- | :--- |
| **状态持久性** | 变化是否需要一个显式的状态载体来"记住" | 需要载体 = 模型必须选对机制（hack 选型）、必须保证可逆与多实例独立，D4.2 断言项成倍增加；不需要载体 = 一条 `:hover {}` 规则即可 |
| **作用范围跨元素** | 变化是否越出被指向元素 | 跨元素要求模型正确构造后代/兄弟选择器与初始隐藏态，这是与 checkbox-hack 同量级的选择器工程；自反馈只需改自身声明 |

**边界示例：**

| 案例 | 档位 | 依据 |
| :--- | :---: | :--- |
| 提交按钮 hover 由蓝变灰 + `transition` | **T2** | 移开即还原；只改自身 |
| 输入框 `:focus` 边框变色 | **T2** | 同上（焦点自反馈） |
| 卡片 hover 上浮 + 阴影加深 | **T2** | 同上 |
| 导航项 hover 展开二级菜单 | **T3** | 跨元素结构性显隐 |
| checkbox-hack 手风琴 / 开关 / 标签页 | **T3** | 状态被保持，需载体 |
| `:target` 灯箱、`<details>` 折叠 | **T3** | 同上 |

**与"一题多档"规则的关系：** `scoring_rubric` §6.6 的"按最高档位标注"照旧。v2.1 之后该规则的行为更合理：一道"装饰动画 + 按钮 hover 换色"的题现在整体落 T2（而非被 hover 一项拽上 T3），而"hover 换色 + 手风琴"仍落 T3——被拽上去的理由是手风琴，不是 hover。

**未纳入的备选方案（留档）：** 曾考虑在 T3 内部再分 T3a（微交互，30%）/ T3b（状态机，50%）。否决理由：档位数从 6 增至 7，`eval_rules.json` 的 `tier` 取值域、附录 B 速查表、第二层的分档位分布统计全部牵动；而 T3a 的技术特征（`transition` + 伪类、无载体、浏览器全面支持）与 T2 完全一致，另立一档没有分类学收益。

## 四、第二层 · 经验难度档（数据反推）

**定位：** 案例的难度**不由人估计，而由被测模型群的实测平均得分决定**。这是经典测验理论（CTT）中 item difficulty 的直接应用——一道题的难度就是其在被试群体上的平均得分（多分题目取平均分）。

### 4.1 难度指标定义

对每个案例 $i$，其**经验难度值**定义为：

$$\bar{s}_i = \frac{1}{N} \sum_{m=1}^{N} s_{i,m}$$

其中 $s_{i,m}$ 是模型 $m$ 在案例 $i$ 上的评测总分（按 scoring_rubric 计，0–10），$N$ 为被测模型数。

- $\bar{s}_i$ **高** → 模型普遍做得好 → 该题**简单**。
- $\bar{s}_i$ **低** → 模型普遍做不好 → 该题**困难**。

（注意方向：与 CTT 的 P 值一致，**高分 = 容易**。）

### 4.2 难度档切分规则

将**全部案例**（跨 T1–T6）的 $\bar{s}_i$ 汇到一起，按分布切三档。切分不用固定阈值（固定阈值会重蹈"人类拍板"覆辙），而用**分布分位数**，保证三档各有足够样本、具备区分度：

| 难度档 | 切分规则（基于全体 $\bar{s}_i$ 的分位数） |
| :---: | :--- |
| **简单** | $\bar{s}_i$ 位于全体的上三分位（得分最高的约 1/3） |
| **中等** | $\bar{s}_i$ 位于全体的中三分位 |
| **困难** | $\bar{s}_i$ 位于全体的下三分位（得分最低的约 1/3） |

> **为什么用分位数而非固定分数线：** 固定线（如"8 分以上算简单"）会让绝大多数静态题挤进"简单"、绝大多数动态题挤进"困难"，退化成"类型档的马甲"。分位数切分强制三档均衡，最大化难度指标的区分度。具体切点（三分位 / 或按分布形状调整为如 25%–50%–25%）待数据到位后据实确定。

### 4.3 区分度校验（防止重蹈旧模型覆辙）

难度档标定后，必须验证它**真的拉开了差距**，否则和旧模型一样无效。校验两项：

1. **档间分离度：** 三档的 $\bar{s}_i$ 均值应显著不同（简单档均值明显高于中等，中等明显高于困难）。若三档均值挤在一起 → 标定失败，说明当前案例池整体区分度不足，需补充更多难/易案例。
2. **档内一致性 + 单题区分度：** 借用 CTT 的 item discrimination——一道"好题"应该是**强模型得分高、弱模型得分低**。若某题所有模型得分都一样（无论高低），它对区分模型无贡献，应标记复查。理想区分度题目其难度值落在中段（分布中部的题目区分能力最强）。

## 五、标定协议（Calibration Protocol）

**这是本模型能否成立的关键。经验难度依赖实测，而实测依赖"用哪些模型、测多少"。以下参数必须钉死并记入评测元数据，否则难度档不可复现、不可比较。**

### 5.1 被测模型群（样本依赖前提）

⚠️ **CTT 难度是样本依赖的**：同一道题在强模型群里显得容易、在弱模型群里显得困难。因此难度档只在**固定的被测模型群**下有意义。

- **模型数下限：** $N \geq 8$（建议 10+）。$N$ 太小则 $\bar{s}_i$ 方差过大、难度估计不可靠。
- **能力梯度要求：** 被测群必须包含**强、中、弱**不同能力档的模型，覆盖能力谱。若全用顶尖模型，所有题都会显得简单，难度档被压缩。
- **登记：** 被测模型清单（含版本）写入 `calibration_meta.json`，作为该版难度标定的一部分。**更换模型群 = 需要重新标定。**

### 5.2 每档样本量下限

- 要谈"得分分布"，每个**类型档** $\geq 15$–20 例才有意义（分布形状需要足够点才能估）。当前每档远未达标，故：
  - **现阶段（每档 < 15 例）：** 只标注 T 档，**不做经验难度标定**，难度档暂记为"待定"。
  - **达标后：** 按第四章执行标定。

### 5.3 标定与重标定触发条件

难度档不是一次性的，遇下列情况需**重新标定**：

1. 被测模型群变更（换模型、加模型、模型版本升级）。
2. 案例池规模显著增长（新增案例可能改变分位数切点）。
3. 评分细则（scoring_rubric）权重或采分点发生实质调整。

### 5.4 标定流程（伪代码）

```
前提：每个类型档案例数已达下限；被测模型群已固定并登记

1. 对案例池中每个案例 i，用 N 个被测模型各生成一次、按 rubric 评分 → 得 s_{i,m}
2. 计算每个案例的经验难度值 s̄_i = mean_m(s_{i,m})
3. 汇集全部 s̄_i（跨 T1–T6），按分位数切分为 简单/中等/困难 三档
4. 区分度校验（§4.3）：
   - 档间分离显著？否 → 补充更易/更难案例后回到步骤 1
   - 标记零区分度单题复查
5. 将每个案例的 (T档, 经验难度档, s̄_i) 写入其 README.md
6. 将被测模型群、切点、标定日期写入 calibration_meta.json
```

## 六、案例标注体系

每个案例最终标注三项：

| 标注项 | 来源 | 示例 |
| :--- | :--- | :--- |
| **动态类型档** | 先验判定（第三章） | T3 |
| **经验难度值 $\bar{s}_i$** | 实测（第四章） | 6.4 |
| **经验难度档** | 分位数切分（第四章） | 中等 |

**综合标注形式：** `T3 · 难度中等（s̄=6.4）`。类型档给出"考什么能力"，难度档给出"实测多难"，二者独立。

> **示例说明正交性：** 假设标定后得到——
> - 某 T1 静态卡片：s̄=8.9 → **简单**
> - 某 T3 `:has()` 表单：s̄=5.1 → **困难**
> - 某 T4 scroll-snap：s̄=7.8 → **简单**（虽是滚动档，但模型做得好）
> - 某 T5 滚动进度条：s̄=4.6 → **困难**
>
> 注意 T4 落入"简单"而 T3 落入"困难"——**这正是两层解耦的价值：类型档序号不代表难度，难度由数据说了算。** 若沿用旧的"档位即难度"假设，就会把 T4 误判为比 T3 难。

## 七、与评分细则（scoring_rubric）的对接

- **tier 字段扩展：** `eval_rules.json` 中 `d2_5_motion.tier` / `d4_1_motion.tier` 取值域由 `{T2, T3}` 扩展为 `{T2, T3, T4, T5, T6}`（T1 无此字段、关闭 D4）。
- **难度档不进 eval_rules：** 难度档是**评测产物**（跑完才知道），不是**评测输入**，故不写入 `eval_rules.json`，只写入案例 README 与 `calibration_meta.json`。

## 附录 A · 难度定义的文献依据

本模型的方法论转向（从人类先验 → 数据反推）有成熟测量学支撑：

1. **经验难度 = CTT 的 item difficulty。** 经典测验理论把题目难度定义为被试答对的比例（多分题目取平均得分），高值代表容易、低值代表困难。本模型的 $\bar{s}_i$ 即多分题目的经典难度指标。
2. **区分度是难度指标的生命线。** 几乎所有对象都得高分或都得低分的题目信息量极低；难度指标必须能拉开差距，这是弃用旧模型的直接理由，也是 §4.3 校验的依据。
3. **样本依赖是 CTT 的固有属性。** 同一题在强/弱模型群下难度值不同，故必须固定并登记被测模型群（§5.1）。
4. **"难度对模型未必单调"警示。** 对 LLM 拟合难度模型时常发现区分度参数 ≤0 或近 0，"难度随能力单调"的前提被违背——这正是"人类先验拍难度会系统性错位"的证据，支持数据反推路线。
5. **IRT 是更强但更贵的替代。** IRT 的 b 参数理论上样本无关，但需大样本估计，现阶段不具备条件。**本模型先用 CTT 落地；待案例池与被测模型规模扩大后，可升级为 IRT 以获得样本无关的难度估计**——这是明确的后续方向。

> 关键参考：CTT item difficulty / discrimination（Assessment Systems、Doran 1980、Hambleton）；IRT 用于 LLM 评测的难度诊断与区分度分析（"Lost in Benchmarks? Rethinking LLM Benchmarking with IRT", 2025；"A Geometric Lens on LLM Abilities through Joint-Embedding IRT", 2025）。具体文献条目见调研笔记。

## 附录 B · 六档技术特性与浏览器基线速查

| 档 | 核心特性 | 浏览器基线注意 |
| :---: | :--- | :--- |
| T1 | flex / grid | 全面支持 |
| T2 | `transition` / `@keyframes` / `animation`；`:hover` / `:focus` / `:active` | 全面支持 |
| T3 | `:checked` / `:target` / `<details>`、后代/兄弟选择器 全面支持；**`:has()` 需较新版本** | 含 `:has()` 的题须锁定较新 Chromium 基线 |
| T4 | `scroll-snap-*` | 全面支持 |
| T5 | `animation-timeline: scroll()` / `view()` | **较新**，部分浏览器需 polyfill；须锁定渲染基线 |
| T6 | `@property` / View Transitions | **最新**；`view-transition-name` 仅最新浏览器可用；**必须锁定渲染基线并记入评测元数据** |

> **基线锁定影响难度标定：** 若评测环境浏览器过旧、T5/T6（及含 `:has()` 的 T3）特性不生效，所有模型都会做不出该效果，$\bar{s}_i$ 被系统性压低、难度被虚高。故渲染基线必须固定并记入 `calibration_meta.json`。
