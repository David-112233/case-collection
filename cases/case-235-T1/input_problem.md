## 2. 写进 input 的取舍（选了最保守的做法）

- **没写进 input：** 被删掉的交互（点击物体弹出商品信息卡、点击吊灯切换夜间模式、拖动旋转视角）；显示器原本循环播放的视频；加载层；书脊上的具体文字；所有具体尺寸、坐标和色值（只写相对位置和颜色名，与 case-224、227 样板一致）；实现手段（WebGL、三维库、模型文件等都不写）。
- **写进了 input：** “以固定视角静态呈现”，与 case-224 的写法相同。
- **“页面没有标题、文字说明、按钮”**：GT 里的信息卡停在屏外、加载层在模型加载完后隐藏，最终画面只有场景，所以写成可判定的结果。
- **光影只写了概括性的一句**（柔和自然、家具下和墙角有阴影、符合物理规律），参照 case-224。目标图地板和侧墙上有斜向的光斑和阴影带，是烘焙贴图的效果，太难精确描述，没有写。
- **地板木板走向、通高柜和书架的格子数**没写：目标图里能数，但数量对作品不是关键，写了会变成细碎条件。

## 3. 需要用户定的事

1. **交互是否全删。** 按用户“固定视角、只保留静态细节、参考 224”的指示，GT 删掉了全部交互，档位改为 T1。来源里“点击吊灯在白天、夜间两套烘焙贴图之间切换并保持”是一个可保持的点击状态，如果想保留它，GT 要加回这一段，档位回到 T3，input 也要补动效约束。
2. **显示器屏幕。** 现为黑底（与目标图一致）。原视频是 30 秒的彩色虚化光斑，若想定格某一帧，需要指定。
3. **竖屏窄视口。** 来源的视场角按竖直方向固定，窄而高的视口（如 375×812）里房间左右会被裁掉一大半，只剩墙角附近一段；GT 保留了这一点。input 只写“随视口高度等比缩放”，没写窄屏下的表现，评测时竖屏视口是否参与需要用户定。
4. **评分可行性。** 页面是一张三维画布，没有可按选择器检查的 DOM 结构，所有条件只能看截图判定（入库时 INDEX 备注也提到这一点）。
5. **加载层保留。** 协调说明建议去掉 Loading 残留；GT 保留了来源的加载层，因为它在 `room.glb` 加载完后就隐藏，最终画面里没有。若用户希望删掉，只需删 `#loader` 一段，不影响画面。
6. **本地渲染核对。** 云端浏览器没有 WebGL，GT 的三维画面只能由用户在本地浏览器打开 raw.githack.com 地址或运行 `gt_check.py` 核对。另：入库时的“已目视核实”看到的是作者的加载预览图，不是三维场景本身。
