## 2. 写进 input 的取舍（选了最保守的做法，待用户确认）

- **写进了音乐：** 音乐是点击后触发的，不是自动播放，属于作品本身的交互结果（播放、循环、停止后回到开头），可以通过页面上的音频状态判定，所以保留在 GT 里，并像样板 case-227 给出图片地址那样在 input 里给出音乐地址。歌曲能否在评测环境里加载属于资源故障，按输出契约 v2 记 UNRESOLVED，不算模型失败。**如果用户认为音频与评分无关，可以从 GT 和 input 里一起删掉**，题目其余部分不受影响。
- **写进了“两种状态下画面静止，没有持续或循环的动画”。** 来源播放时机身随音乐左右摇摆、投影伸缩，GT 按准静态要求去掉了，这句是 GT 的设计结果。不写的话模型照来源加上摇摆也合规，但会让按键、仓门位置类规则难以判定。如果用户认为这句属于从 GT 反推的新要求，可以删掉。
- **没写“切换瞬时完成”：** 去掉仓门 0.2s、按键 0.1s 过渡是 GT 的简化，不是作品要表达的效果，所以 input 只要求切换后保持状态，不限制有无过渡。
- **悬停效果写进了动效约束：** 播放键悬停变深、喇叭图标悬停放大都在 GT 里且可判定。播放键的变化很小（#ff7814 到 #ff6f04），评测时可能难以判定；如果用户认为太细，可以删掉这一句。
- **没写进 input：** 整个页面的手形指针（`body` 上的 `cursor: pointer`，与题目核心无关）；机身背面、左侧面、底面（默认视角看不到）；机身底下比机身略大的一圈深色底边（`.shadow-2`，很窄，与投影合在一起描述）；所有具体尺寸和色值（只写相对关系和颜色名，与 case-224、227 样板一致）。
- **“页面不出现滚动条”：** 来源 `body` 为 100% 宽、100vh 高且 `overflow: hidden`，作为可判定结果写入。

## 3. 需要用户定的事

1. 第 1 节的推算要在本地渲染核对后才能确认；方向或细节有误时按截图改写 `layout_constraints`。
2. 音乐是否保留在 GT 和 input 里（我的默认：保留）。
3. 是否保留“没有持续或循环的动画”一句（我的默认：保留，与 case-228 一致）。
4. 播放键悬停变深是否保留（我的默认：保留）。
5. 作品的看点之一是播放时机身随音乐摇摆，准静态 GT 去掉后，题目的难点集中在立体机身、内凹磁带仓、倾斜仓门和点击后的状态切换上；档位复核为 T3，不改名。如果用户认为去掉摇摆后作品价值不足，可以不收。
