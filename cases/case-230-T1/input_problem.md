# case-230 input 的问题与取舍（2026-11-24，duet）

## 1. 外观描述由 CSS 推算，待本地渲染核对

本环境无法渲染 GT（装不了 Chromium，见 [review_20261124/static_check.md](review_20261124/static_check.md)）。下列描述是从 CSS 推算的，需在本地运行 `review_20261124/shot_gt.py` 后对照截图核对：

| input 描述 | 推断依据 | 风险 |
|---|---|---|
| 白色纸片“相对蓝色字母略向左上偏移，向右上方微微翘起，越往右越高” | `::after` 以左下角为原点 `translate(-4px,-2px)` 加 `skew(-2deg,-6deg)`；父元素无 `perspective`，`rotateY(11deg)` 只让字母水平略窄约 2% | 方向判断错会让整段外观失真，最需要核对 |
| 蓝色只在下边和右边露出楔形窄边，越靠右越宽 | 白色字母上移 2px、左移 4px 且右侧抬高，蓝色字母原位不动 | 露出的宽度很小（推算约几到十几像素），评测时是否容易判定待看截图 |
| 灰色阴影略向下、向右下倾斜，在下边和右边透出暗边 | `::before` 透明文字，`skew(0,3deg)`，`text-shadow: 0 3px 5px rgba(0,0,0,.25)`；它画在蓝色字母之上、白色纸片之下 | 阴影很淡，可能只是蓝边略发暗，单独看不出“暗边” |
| 白色纸片“与背景几乎同色，带极浅的白到浅灰横向渐变” | 渐变 `#FFF → #EEE`，背景为默认白色 | 纸片轮廓在白底上是否可辨待核对 |
| 五个字母在一行内居中 | 估算总宽约 590px | 只对桌面宽屏成立；375 视口估计会换成两行，所以 input 写了“面向桌面宽屏” |

## 2. 写进 input 的取舍（选了最保守的做法，待用户确认）

- **写成三层叠字**：功能里写“白色纸片、露出的蓝色同形字母、灰色阴影”三层。这是画面上能看到的组成，不是指定伪元素或 `transform` 等手段；如果用户认为这已经接近实现描述，可以改成只描述最终观感。
- **颜色只写颜色名**（纯白、明亮的天蓝色、白到浅灰），没写 `#32A8E0`，也没写字号 128px、倾斜角度、偏移像素，与 case-224、227 样板一致。若想让颜色可严格判定，可以把色值加进去。
- **字体只写“粗体无衬线”**，没写 Helvetica。来源只写了本地字体名 Helvetica、无回退，各系统显示不一；写进 input 会让字体条件依赖评测环境。
- **写了 `motion_constraints`“完全静止、无交互”**：来源本身就没有任何动态，这一句描述的是作品原貌，不是 GT 简化的结果。样板 224、227 没写这一段；如果用户认为不需要，可以删掉。
- **没写进 input**：标题上方空白的具体高度（只写“明显的空白”）；`rotateY`、`translateZ` 带来的几乎不可见的变化；来源里被浏览器忽略的无效声明。

## 3. 作品本身的难度提醒

入库评语已指出“关系较单一，难度不应因视觉效果而夸大”。按推算，作品的可判定点集中在一个效果上（白色纸片翘起、蓝边露出、阴影），条件数量会很少。是否仍收录、以及这几条外观描述是否足够区分模型，请用户看截图后定。

## 4. 需要用户定的事

1. 第 1 节的推算需要本地渲染核对；方向或可见度有误时，按截图改写 `layout_constraints`。
2. 颜色是否要写色值。
3. 是否保留 `motion_constraints` 这一句。
