## 1. 问题一：我能否替代"人工上 CodePen 找 → 下载 ZIP"

**结论：能，发现和获取都可以由我自动完成，不需要你手动下载 ZIP。** 以下均为今天实测：

| 环节 | 测试 | 结果 |
|---|---|---|
| 直接浏览 codepen.io | 内置浏览器打开搜索页 | Cloudflare Turnstile 人机验证，**我按规则不能代点** |
| 命令行访问 codepen.io（作品页、`.css/.html` 后缀、RSS、oEmbed） | curl | 全部 403 |
| **发现作品** | WebSearch：`site:codepen.io pure CSS scroll-driven animation no JavaScript` | **可用**，单次返回约 9 个作品链接 |
| **获取源码** | `https://cdpn.io/{作者}/fullpage/{作品ID}` | **200，不受拦截**；页面 `srcdoc` 内含编译后的完整 HTML + CSS，并带 canonical 原始 URL 与标题 |
| 自动判 JS | 抽 3 个作品解析 `srcdoc` | 纯 CSS 作品只有 CodePen 自动注入的 `window.console = …` 一行样板（可安全剔除）；jh3y/MWLPMYL 含 5.9K 字符用户 JS，可自动识别并标注，是否改造由人工判断 |
| 许可 | CodePen 官方文档 | 公开作品默认 MIT；私有作品无许可（私有作品本就无法公开访问） |

**与 ZIP 的差别**：`fullpage` 给的是编译后结果（等价于 ZIP 的 `dist/`），没有 SCSS 原稿和 README。现有流水线本来就优先用编译 CSS，影响不大；作者、URL 由 canonical 链接得到。

**拟实现流程**（新增一个脚本，产出直接接入现有 `prepare → classify → evolve`）：

1. **发现**：我按"档位 × 难度机制"关键词矩阵（§3.3）批量 WebSearch，另从 GitHub awesome 列表（如 css-art 类）和知名作者（argyleink、jh3y、hexagoncircle、bramus、Temani Afif 等）的作品收集候选 URL。
2. **获取**：逐个请求 `cdpn.io/.../fullpage/...`，限速约每 2 秒 1 个，只取公开作品。
3. **自动初筛**：已采过同一 URL → 跳过；JS 只标注不拒收（2026-10-02 用户确认含 JS 作品可改造收入，见 B1 工作方案 §4）；按 §3 难度特征打分。
4. **落盘**：写成与现有 `collect_codepen.py` 相同的 `source.html + metadata.json`（加 `acquisition: cdpn_fullpage`），后续流程不变。

可选增强：如果你愿意在内置浏览器里亲手点一次 Cloudflare 验证，我就能浏览 CodePen 的 tag 页、热门页，候选质量会更高；不点也能跑。

## 3. 问题三：怎样算"够难"

### 3.1 现有证据

- 历史 56 例 pilot（2026-09 快照、旧评分口径）：DeepSeek 均分 9.27、56 例中 40 例满分，"困难组"反而比"简单组"分高，**天花板效应明显**。
- 同期诊断发现评分存在误放行（把源码声明当成实际效果等），所以部分"简单"是评分偏松造成的，不全是题目简单。
- 按新方法重建的 case-135（多阶段精确时间编排的 3D 几何）得 3/2 分；case-156（纯 CSS 扫雷）DeepSeek 8、Qwen 3。两例都属于"多状态 + 精确约束"，确实拉开了差距。

### 3.2 与现有规则的边界（需要你确认）

AGENTS 禁止"为了均分递减、箱线图好看而改分或调难度"，DATA-001 Packet 写了"不按预期分数筛题"。"专挑模型不擅长的题"本身是正当的基准设计（许多难题集都这样做），但属于科研口径变化，需要登记为一条决策：

- **允许**：按**先验难度特征**（§3.3）在冻结前挑题；
- **可选**：用**不参与正式评测的探针模型**做小规模预筛，淘汰明显太简单的题，并在论文中写明；
- **禁止**：用正式被测模型的得分挑题，或在看到输出后改题。

### 3.3 候选难度特征（先验、可在采集时判断）

每个候选按命中特征计分，达到阈值才进入候选池；阈值待定（Q4），可先用 ≥3 项试跑。

| 编号 | 特征 | 说明 | 主要对应档位 |
|---|---|---|---|
| H1 | 多状态耦合 | ≥3 个相互影响的状态载体（checkbox/radio/`:target`/`:has()`），如纯 CSS 游戏、多步表单 | T3、T6 |
| H2 | 一处触发、多处联动 | 一个操作同时改变多个相距较远的元素，且要求可逆、多实例互不干扰 | T3、T4 |
| H3 | 精确时间编排 | ≥3 个阶段的 keyframes，有明确时长、错峰、循环衔接要求 | T2、T6 |
| H4 | 新特性 | `animation-timeline`/`view()`、`@property`、`:has()`、容器查询、anchor positioning、View Transitions、scroll-state 查询 | T5、T6 |
| H5 | 几何/3D 精度 | 3D 变换、多面体、复杂 `clip-path`/`conic-gradient` 图形 | T1、T6 |
| H6 | 计算内容 | CSS 计数器、`counter()` 计分、纯 CSS 图表 | T6 |
| H7 | 大体量真实布局 | 多区块、多组件、响应式断点多的完整页面（非单个组件） | T1、T4 |
| H8 | 组合机制 | snap 与状态、滚动驱动与 hover 等两种以上机制叠加 | T4—T6 |

**一票否决**（太简单）：单组件演示（单按钮、单加载图标、单卡片 hover）、纯装饰循环动画、机制只有一条 CSS 规则即可实现的作品。

T4 的特殊问题：scroll-snap 本身机制简单，要够难只能靠 H2/H7/H8（大页面 + snap + 联动）。但按"就高标注"规则，snap + 滚动驱动会被标为 T5，所以 **T4 补到 75 例且每例都难，可能做不到**，见 Q5。

### 3.4 后验校准

新批次冻结后，用被测模型群实测，按难度模型第四章做分位数难度分档；若新批次整体仍在高分区，据此调整**下一批**的特征阈值，不回改本批。

## 4. 产能与瓶颈

- 发现和获取已可自动化，每天数百个候选没有问题。粗估：搜到的作品约 1/3 是纯 CSS，再经难度筛选约 1/5 留下，补 240 例约需 1000—1500 个候选（估算，首批试跑后修正）。
- **真正的瓶颈在采集之后**：每例都要写 `input.json`、生成并自测 GT、审核和冻结规则。扩量速度取决于这部分，建议 DATA-002 同时规划 input 编写产能。

## 5. 建议的第一步

先做一批 **30 个候选试跑**（T1 10 个、T4 10 个、T6 或 T3 10 个）：实现 cdpn 获取脚本，跑发现 → 获取 → JS 过滤 → 难度打分 → 接入 `prepare`，统计纯 CSS 率、难度通过率和单例耗时，再决定规模化参数。试跑只落地源码和元数据，不写 input/GT，不调用生成模型。
