# input 精简与考点强化

目标：让 input **短而准**——不告诉模型怎么做，只说要达到什么结果；把分数集中在这道题真正难、真正需要模型思考的地方。方法来自 case-105 v2（input 从 1,463 字减到 859 字，新增单星、星线同步、圆润树等考点）和 case-004 v2（删去提示，改按常识考查）。完整范例见 105 修改方案、105 问题报告、105 估分。

## 先读

[AGENTS](../../../AGENTS.md)（硬规则）、[评分细则 v6](../../docs/scoring_rubric_v6.md)、目标案例的 `input.json`、`ground_truth.html`、源码（`source.*`）和现有规则 `rules_drafts/*/eval_rules.json`。写规则细节时配合 [eval-rules-refinement](../eval-rules-refinement/SKILL.md)。

## 决定权（DEC-039）

流程中的取舍由执行者**自行决定**，不逐例停下来问用户：新增或删除哪些要求、常识条目、源码继承数值的去留、冻结。每项决定都写进方案文档的“自行决定事项”表，附一句理由；冻结记录的 `status` 写 `AGENT_DECIDED`。用户事后抽查，评测出了问题再另立版本修订。

下列事项不在自行决定的范围内：

- 看到模型输出后，为了调分去改题。本流程只能在另立新版本时使用，且新版本必须重新生成输出。
- 为了多扣分把条件拆细（DEC-038）。
- 用 GT 反推新增要求。
- 改计分公式、严重度定义等科研口径。

## 第一段：分析

**1. 确定难点。** 读源码和 GT，用一两句话写出这道题最需要模型自己思考的是什么。例如 105 的难点是“星星随滚动把树画出来，并且和线条同步”，而不是颜色和尺寸。

**2. 实测，核对 input 有没有把难点送掉。** 有现成的被测输出就在浏览器里量，不靠肉眼印象；滚动或动画类题目可以用 [scroll_trace_probe.py](scroll_trace_probe.py)。核对两件事：

- 照着 input 做的模型，是否轻易拿下了难点？如果是，input 里很可能有实现说明。
- 偷懒的做法（梯形树、多个星星接力）是否也能通过现有规则？如果能，说明难点没有要求，或者要求太弱。

**3. 按五类问题标记 input 语句。**

| 类别 | 识别方法 | 105 的例子 |
|---|---|---|
| 实现说明 | 直接或换个说法说出 CSS 属性、技术手段、检测方式 | “将滚动进度连续映射为纯 CSS 动画进度；沿二维路径定位移动；连续改变轮廓线显现比例” |
| 分镜式叙述 | 把每一步的顺序、动作都写死，模型不用自己编排 | “依次移动到 3 个装饰球上，分别沿轮廓环绕一周……离开最后一个装饰球……” |
| 评测语言 | 写给评测器的话：比较方法、判定前提、“不按……判断” | “因此可在同一状态比较二者的位置”“能力须通过独立于页面实现的环境检测确认” |
| 难点没有要求或要求太弱 | 偷懒的做法也能满足字面意思 | “单独的树形轮廓插画”“1 个星形”、规则里的“可见关联” |
| 含糊或做不到 | 用“可”“优先”等不构成义务的词；关键状态没说；和项目政策冲突 | “可整体缩小”“高视口优先展示”、标题开始时是否显示没说、禁止外部字体却要求“手写衬线字体” |

**4.（可选）参考外部研究。** 只在新的题型或大类第一次处理时做。找已有 Benchmark 里和输入形式无关的模型弱点，比如路径和轨迹、插画造型、“能跑但不对”；精确复现类的结论参考价值低。结论放在 `docs/research/`，之后的同类案例直接引用。已有调研：CSS 动画 Benchmark 调研。

问题清单写到案例目录的 `input_problem.md`：一张表，列出问题、位置、证据与影响、修改方向。

## 第二段：处理

**5. 以 Requirement 为单位，逐条做删除测试。** 对每条 Requirement 找出它对应的 input 语句，然后问：

> 删掉（或精简）这句话之后，模型还能从其余语句合理推断出同样的结果吗？

- **能推断，就删除或精简。** Requirement 保留，规则里给对应条件加 `source_note`，说明由哪句推断。例如“固定在视口”可以从“随滚动观看画图”推断出来，这本身就是考点。
- **不能推断，就保留。** 具体颜色、尺寸、文案、数量都属于这一类。源码继承来的数值默认保留，除非它和其他要求冲突。
- **实现说明和评测语言一律删除。** 评测需要的环境和判定前提，写进规则的顶层字段，例如 `capability_environments`。
- **重复的只留一处。** forbidden 与功能描述重复、同一显隐条件写两遍，都属于这种情况。
- **不对应任何 Requirement 的句子**（如“不需要导航、按钮……”）可以删除。

**6. 给难点补上只写结果的要求。**

- 写结果，不写手段。例如“星形始终位于正在延伸的线条末端”，不写 `offset-path`。
- 用明确的说法堵住偷懒做法：“只有这一个……，整个过程中始终是同一个”“不能只用直线折线拼成”。
- 必须能判定：要么能用程序测（距离、数量、是否在视口内），要么是 Judge 能明确判断的事实。美感等主观项留给外观评分，不写进 input。
- **不加通用条款**（如“所有文字须完整可读”）。已要求元素的基本可用性按常识（DEC-037）计分：规则条件标 `common_sense` 并写理由，input 里不写，免得把考点说出来（004 的经验）。
- 新要求如果会让原来的某种做法变成错，这是正常的；把理由写进“自行决定事项”。

**7. 写修改方案**，文件为案例目录的 `input_revision_plan_v<N>.md`，结构如下：

1. 依据与审查标准（各一段）。
2. 逐条审查表：Requirement｜对应 input 语句（现状）｜判断｜处理。
3. 修改后的 input 全文（JSON 代码块，字段顺序和原文件一致）。
4. 篇幅对比（功能、布局、动效三段的字数，前后各一个数）。
5. 对规则的影响：新增或加严、常识条件、改为推断来源、删除的条件和门禁、环境定义。
6. 自行决定事项表：事项｜决定｜理由。

## 第三段：执行与验证

**8. 归档与登记。**

- 把旧版本的 `input.json`、`ground_truth.html`、`rules_drafts/manual_v*/` 原样复制到 `versions/v<旧>/`，并核对哈希与旧冻结记录一致。
- 在 TASKS 的“当前写入”登记写入范围，并加一行任务。
- 不改 `evaluation_runtime/` 下的旧运行产物。

**9. 写新 input。** 直接从方案文档的 JSON 代码块读取后写入，避免手抄出错。

**10. 写新规则** `rules_drafts/manual_v<N>/eval_rules.json`：用脚本在旧规则基础上修改，不要手工改大段 JSON。

- 推断来的条件加 `source_note`。
- 常识条件 `source_fields` 写 `["common_sense"]`，并附 `common_sense_rationale`。
- 新考点写成可测的条件，测量方法写清楚，例如“程序测量星形中心到线条末端的距离，约 16px 以内”。
- 删除条件后，条件编号重新连续排列，并检查对旧编号的引用。
- 顶层更新 `input_sha256`、`source_policy`、`revision_note`；`scoring` 写成 `{"policy": "evidence-severity/1.0"}`，旧公式块不要保留。
- 校验：ID 唯一、条件编号连续、`depends_on` 引用存在、常识条件都有理由。

**11. GT 自检。** 新增的每一条要求都要在 GT 上实测通过。GT 不满足时，先判断是要求写得不对，还是 GT 有缺陷：要求不对就改要求，GT 有缺陷就修 GT。**GT 不能反过来成为要求的来源。** 涉及回退分支的，要分别在支持和不支持的环境里测；Playwright 自带的 Firefox 可以充当“不支持滚动时间线”的环境，用前先用 `CSS.supports` 核对。

**12. 冻结。** 写 `FREEZE_v<N>.json`：

- 三份文件的哈希，以及生成 Prompt 的路径和哈希。
- `status`：用户确认过的写 `FROZEN_BY_USER`，按 DEC-039 自行决定的写 `AGENT_DECIDED`。
- 指向旧版本的路径。
- 注明旧输出不用于新版本。

不要覆盖旧的 `FREEZE.json`。

**13. 生成输出，按需要估分。**

- 生成命令见 模型生成 README。输出命名为 `case-XXX-v<N>-<model>.html`，不得覆盖旧输出。
- 估分时按规则逐条判断，失败的条件写依据和严重度（轻 0.5、中 1、重 1.5）。按 DEC-029，上游失败实际阻断的下游条件也判 FAIL。
- 结果写成 `score_estimate_v<N>_<model>.md`，注明“非正式估分”。
- 可以用改过的诊断副本来观察模型的其他能力，但只能放在暂存目录，并且注明不计分。

## 常见坑

- 只删不补：删光实现说明后，如果不给难点写出可判定的要求，偷懒做法照样能通过。
- 把手段当结果：例如“用 position: fixed 固定”是手段，“滚动时画面始终在视口内”才是结果。
- 删除后忘了在规则里补 `source_note`，结果这条要求失去了来源。
- 新要求写得过细（固定像素、固定段数），等于另一种实现说明。
- 删除测试做得太激进：颜色、文案、数量这类事实一旦删掉，模型就无从推断。
